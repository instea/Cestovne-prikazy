2. Features by area

Auth and session

  • User signs in with Google; server verifies the ID token against CLIENT_ID. (analysis: §2.1 Auth / session)
  • Login returns WRONG_DOMAIN and creates no user when HOSTED_DOMAIN is set and the token domain differs. (analysis: §2.1 Auth / session, §2.8 Auth)
  • First login of an unknown email auto-creates an unapproved, non-admin user (id = Google sub, names from token) and returns NEED_APPROVAL. (analysis: §2.1 Auth / session)
  • Unapproved user gets NEED_APPROVAL; approved user gets SUCCESS and a 1-hour JWT. (analysis: §2.1 Auth / session)
  • Failed token verification returns FAILED. (analysis: §2.1 Auth / session)
  • Login page shows "Login failed. Try again later.", "Used email does not belong to given hosted domain." or "Account needs to be approved by admin first.". (analysis: §2.4 Screens)
  • JWT is kept in browser localStorage; app auto-logs-in on reload and logs out if the user info call returns nothing. (analysis: §2.1 Auth / session, §2.8 Auth)
  • JWT is refreshed every 15 minutes via POST /refresh-jwt. (analysis: §2.1 Auth / session)
  • Logout removes the JWT and resets the client cache. (analysis: §2.1 Auth / session)
  • CLI command promotes a user (by email) to admin and approved. (analysis: §1 Overview, §2.1 Auth / session)
  • CHANGE Refreshed JWT is always stored, the refresh timer runs after a fresh login too, and an expired stored JWT sends the user to login. (interview: Rewrite goal › Functional bugs; analysis: §8 Risks)
  • CHANGE Auth middleware never hangs a request on unexpected errors. (interview: Rewrite goal › Functional bugs; analysis: §8 Risks)
  • CHANGE Client data loading recovers after an API error without a page reload. (interview: Rewrite goal › Functional bugs; analysis: §8 Risks)
  • PRESERVED BUG /refresh-jwt issues a new token for expired or invalid tokens without checking the user or approval. (interview: Rewrite goal › Security bugs; analysis: §8 Risks)
  • PRESERVED BUG Invalid JWT is treated as anonymous; approval is not re-checked per request; denied calls return null (HTTP 200), not 401. (analysis: §2.3 Roles)

Users

  • Admin lists users: Email, Name (surname[, firstName][, degrees]), Is admin, Is approved. (analysis: §2.1 Users, §2.4 Screens)
  • Admin approves an unapproved user, who can then log in. (analysis: §2.1 Users, §2.8 Users)
  • Admin edits and removes users. (analysis: §2.1 Users)
  • User edits own profile (first name, surname, degrees, address); email and approved are read-only; "Is admin" is hidden for non-admins. (analysis: §2.1 Users, §2.8 Users)
  • Trips and leaves of a deleted user show placeholder "Deleted" / id / <id>@deleted.instea.co. (analysis: §2.1 Users)
  • CHANGE Regular users can read only their own user record; admin reads all. (interview: Data visibility)
  • PRESERVED BUG Any user can update any user's email, approved flag and names via updateUser; only isAdmin is protected. (interview: Rewrite goal › Security bugs; analysis: §8 Risks)
  • PRESERVED BUG User edit page has an empty header, and after save a non-admin lands on /users and sees "You are not authorized to view this page!". (analysis: §2.4 Screens)

Trips

  • User sees the trips table: Who, Destination, When (D. M. YYYY[ - D. M. YYYY]), Controls; sorted by departure ascending. (analysis: §2.1 Trips, §2.4 Screens)
  • CHANGE Regular user sees only own trips; admin sees all. (interview: Data visibility)
  • User adds a trip: Who, Where, departure, arrival, purpose, travel type (O, R, A, L, DZ, AUS, AUV, MOS, MOV), price; defaults yesterday 08:00–17:00, type O. (analysis: §2.1 Trips, §2.8 Trips)
  • CHANGE Non-admin can add a trip in the UI. (interview: Rewrite goal › Functional bugs › Trip permissions)
  • CHANGE Trip owner or admin can edit and remove a trip; the server checks the trip owner. (interview: Rewrite goal › Functional bugs › Trip permissions)
  • CHANGE UI shows an error when a trip save is denied, instead of navigating as if saved. (interview: Rewrite goal › Functional bugs › Trip permissions)
  • Owner or admin removes a trip without confirmation. (analysis: §2.4 Screens)
  • Owner or admin duplicates a trip: new departure, arrival keeps the original duration, other fields copied. (analysis: §2.1 Trips, §2.6 Trip duplication)
  • PRESERVED BUG Server accepts any userId on trip create (user can create trips for others). (interview: Rewrite goal › Security bugs; analysis: §2.3 Roles)
  • PRESERVED BUG Arrival-after-departure is not validated on client or server. (interview: Rewrite goal › Other bugs; analysis: §2.2 Data model)

Places

  • User lists places: Name, Destination name, Origin name, Travel duration (2h 30m). (analysis: §2.1 Places, §2.4 Screens)
  • Admin adds, edits and removes places: name, destination name, origin name, travel duration (slider 0–1440 min, step 15, stored as ISO-8601), country (243 ISO codes, default SK). (analysis: §2.1 Places, §2.2 Data model)
  • Non-admin sees a read-only list; add/edit pages show "You are not authorized to view this page!". (analysis: §2.8 Places)

Travel-warrant export

  • User picks a person and a month (years 2017..current) and generates a travel-warrant xlsx, then downloads it. (analysis: §2.1 Travel-warrant export, §2.4 Screens)
  • Non-admin person picker shows only the user. (analysis: §2.3 Roles)
  • Template is chosen by trips departing in the month: 0–9 → upto19, 10–15 → upto31. (analysis: §2.6 Template choice)
  • Template is filled with name/degrees/address and per-trip left rows and right 4-row blocks (dates, origin/destination, times ± travel duration, travel type, price, diet). (analysis: §2.6 Template filling)
  • Per-diem by country and whole-trip hours: SK 4.5 / 6.7 / 10.3 €; foreign 25 / 50 / 100 % of tariff; unknown country 0. (analysis: §2.6 Per-diem)
  • Non-EUR diet tariffs are converted to EUR via an exchange-rate source (source: open question S1). (analysis: §2.6 Per-diem, §4 Integrations)
  • Cached formula values are stripped so Excel recalculates totals. (analysis: §2.6 Template filling)
  • PRESERVED BUG 16 or more trips in a month fail with HTTP 500 / "Problem preparing file". (interview: Rewrite goal › Other bugs; analysis: §2.6 Template choice)
  • PRESERVED BUG SK trips under 5 h get 6.7 €; multi-day trips are not split per day. (interview: Rewrite goal › Rule quirks; analysis: §2.6 Per-diem)
  • PRESERVED BUG Origin "Bratislava" is hardcoded; upto31 totals sum only R7:R44; approver name is static template text. (analysis: §2.6 Template filling)
  • PRESERVED BUG Server accepts any userId for export; generated files are public under /download with random names and never deleted. (interview: Rewrite goal › Security bugs; analysis: §8 Risks)

Leaves

  • CHANGE Regular user sees only own leaves in list and calendar; admin sees all. (interview: Data visibility)
  • User lists leaves: Requester, Days (start - end (N work days), ? if unknown), Type, State, Approver, Delete. (analysis: §2.1 Leaves, §2.4 Screens)
  • User filters leaves by requester, month and year (leaves split into per-year segments) and clears the filter. (analysis: §2.6 Leave filter)
  • User switches to a calendar of non-rejected leaves: color per requester (15-color round robin), pending at half opacity, title First Surname [1/2 ](T). (analysis: §2.4 Screens, §2.6 Calendar colours)
  • User adds a leave: type (ANNUAL, SICKNESS, DOCTOR, MATERNITY, PARENTAL, CARING; default ANNUAL), start (default today), end (follows start until edited), half-day; work days shown. (analysis: §2.1 Leaves, §2.4 Screens)
  • Work days = weekdays that are not SK public holidays; half-day subtracts 0.5. (analysis: §2.6 Work-day count)
  • Add form shows "Start date must not be greater than end date" and "Half day option is allowed only within single day". (analysis: §2.4 Screens, §2.8 Leaves)
  • Server creates the leave as PENDING with requester = caller and emails the approver. (analysis: §2.1 Leaves)
  • Requester or admin deletes a leave in any state, without confirmation. (analysis: §2.1 Leaves, §2.3 Roles)
  • PRESERVED BUG Delete button shows on every row and silently fails for others' leaves. (interview: Rewrite goal › Other bugs; analysis: §2.3 Roles)
  • PRESERVED BUG Server does not validate leave dates, half-day rule or overlaps and trusts client numDays. (interview: Rewrite goal › Other bugs; analysis: §2.2 Data model)
  • PRESERVED BUG Half-day subtracts 0.5 for any range length. (analysis: §2.6 Work-day count)
  • PRESERVED BUG "Add leave" may be always disabled (Angular group-validator bug); runtime behavior is unverified, see open questions S2 and A2. (interview: Rewrite goal › Other bugs; analysis: §8 Risks)

Leave approval

  • Admin sees pending leaves and approves or rejects them; approver is set and the row disappears. (analysis: §2.1 Leaves, §2.4 Screens, §2.8 Leaves)
  • Admin nav shows a badge with the pending-leave count. (analysis: §2.1 Leaves)
  • PRESERVED BUG Approval page is reachable by non-admins (clicks silently fail); leaves can be re-approved or re-rejected in any state; no email on decision. (interview: Rewrite goal › Other bugs; analysis: §2.3 Roles, §8 Risks)

Leave summary

  • User sees own leaves per year (descending), per type, with total work days; leaves crossing a year are clipped. (analysis: §2.1 Leaves, §2.6 Summary)
  • PRESERVED BUG Summary counts PENDING and REJECTED leaves. (interview: Rewrite goal › Rule quirks; analysis: §2.6 Summary)

Detail export (meal vouchers)

  • User picks a person (all users listed) and a month and downloads an xlsx: name, month, trips count, leaves count, expected meal vouchers, trip days, leave days, leave types, "HALF DAY". (analysis: §2.1 Leaves, §2.6 Detail export)
  • Working day = not SK holiday and not weekend; trip and leave days are unique sorted working days. (analysis: §2.6 Detail export)
  • Expected meal vouchers = month working days − trip days − leave days + half days. (analysis: §2.6 Detail export)
  • PRESERVED BUG PENDING and REJECTED leaves are counted; month working days include the 1st of the next month. (interview: Rewrite goal › Rule quirks; analysis: §2.6 Detail export)
  • PRESERVED BUG Server accepts any userId for export. (interview: Rewrite goal › Security bugs; analysis: §2.3 Roles)

Attendance API (M2M)

  • M2M client calls GET /api/attendence/:year/:month with Basic auth; 401 when credentials are wrong or unset. (analysis: §2.1 Attendance API, §2.5 API contract)
  • Response lists SSO users with a Toggl id; only employee === '1' get daily hours, leave codes and total, plus contractType. (analysis: §2.6 Attendance)
  • Hours come from Toggl Reports v3 per user token, paginated with a 500 ms pause. (analysis: §2.6 Attendance)
  • APPROVED leaves on working days map to codes D8 / D4 (half day) / PN / L / I, joined with ", ". (analysis: §2.6 Attendance)
  • Errors: 400 "Month is not a number." / "Year is not a number."; 500 "Cannot get data from SSO, try again later." / "Cannot get data from Toggl, try again later.". (analysis: §2.5 API contract)
  • Dates use DEFAULT_TIMEZONE (default Europe/Bratislava). (analysis: §2.6 Attendance)
  • PRESERVED BUG Request crashes on an employee without togglUserId or an unknown Toggl user; duplicate SSO names overwrite each other. (analysis: §8 Risks)

Notifications

  • New leave sends "New leave notification" email to APPROVAL_MAIL_RECEIVER: requester, dates, type, "Approve" link to the approval page. (analysis: §2.7 Notifications)
  • Missing SMTP settings only log, they do not fail leave creation. (analysis: §2.7 Notifications)
  • PRESERVED BUG User names are not HTML-escaped in the email. (analysis: §8 Risks)

Operations

  • /health-check pings Mongo: 200 {checkMongo:'ok'} or 500 with the error. (analysis: §2.1 Ops, §2.5 API contract)
  • Process exits on Mongo connect failure or disconnect, so Kubernetes restarts the pod. (analysis: §1 Overview)
  • PRESERVED BUG GraphiQL is public and CORS allows all origins. (interview: Rewrite goal › Security bugs; analysis: §8 Risks)

Data and validation

  • Data model: Place, User, Trip, Leave with app-level id (UUID or Google sub) and indexes as today. (analysis: §2.2 Data model)
  • PRESERVED BUG Server enforces no required fields beyond GraphQL non-null inputs. (interview: Rewrite goal › Other bugs; analysis: §2.2 Data model)

3. User decisions

Testing

  • Every feature has automated tests; humans and AI agents both write code, so tests are mandatory and a coverage gate runs in CI. (interview: AI agents)
  • Tests are written only in the new app, from the analysis acceptance criteria and worked examples; no golden comparison with the old system. (interview: Tests)
  • Unit tests cover all business rules: per-diem, template choice, template filling, work days, meal vouchers, leave filter, calendar colors, summary, attendance codes. (interview: Tests; analysis: §2.6 Business rules)
  • Integration tests cover every GraphQL operation and REST endpoint, including the permission matrix and the preserved bugs. (interview: Tests; analysis: §2.3 Roles, §2.5 API contract)
  • End-to-end tests cover the main screens: login, trips, places, users, both exports, leaves list/calendar/add/approval/summary. (interview: Tests; analysis: §2.4 Screens)
  • Contract tests freeze the attendance API: JSON shape, status codes, error messages, attendance codes. (interview: M2M contract)
  • External integrations are replaced in tests by fakes kept in the repo: mail catcher, SSO stub, Toggl stub, fake Google token issuer, mocked exchange rates. (interview: Integration testability)

Environments

  • Local docker-compose runs the full stack with integration fakes; no hosted staging environment. (interview: Environments)
  • Script creates an anonymized copy of production MongoDB (names, emails, addresses) for local testing and migration rehearsal. (interview: Prod data)
  • AI agents work with code and the local docker-compose environment (fakes, anonymized data); no production access. (interview: AI agent access)

Integrations

  • Integration reference document for Google Identity, SSO directory, Toggl Reports v3, SMTP, exchange-rate source and the M2M consumer: endpoints, auth, fields, error behavior. (interview: Integration docs)

Scope

  • Security bugs are preserved 1:1. (interview: Rewrite goal › Security bugs)
  • Business-rule quirks are preserved 1:1. (interview: Rewrite goal › Rule quirks)
  • Export over 15 trips and leave validation/state bugs are preserved 1:1. (interview: Rewrite goal › Other bugs)
  • Trip permission bugs and session/refresh bugs are fixed. (interview: Rewrite goal › Functional bugs)
  • Regular users see only their own trips, leaves and user record; admin sees all. (interview: Data visibility)
  • The two SPAs become one React SPA; the GraphQL + REST contract stays the same. (interview: Target tech stack › Frontend; interview: API style)

Documentation

  • Business rules document (diets, meal vouchers, work days, attendance codes, leave filter), validated by the domain expert. (interview: Documentation)

Migration strategy

  • Migration goes module by module; cutover can happen at any time in the month. (interview: Migration; interview: Cutover)
  • Step 1, Leaves: new SPA leave screens and leave API go live; ingress routes /leaves/ to the new app; the old app still serves Trips. (interview: Migration)
  • Step 2, Trips, Places, Users, travel-warrant and detail exports: new screens and API go live; ingress routes / to the new app. (interview: Migration)
  • Step 3, Attendance API: /api/attendence moves to the new server after its contract tests pass. (interview: Migration; interview: M2M contract)
  • Old and new app share one MongoDB and one JWT signing key during the transition, so a session works across both. (interview: Migration)
  • Each step is rehearsed locally on the anonymized prod copy before go-live. (interview: Prod data)
  • Rollback per step: route the ingress path back to the old deployment. (interview: Migration)
  • MongoDB 3.6 is upgraded to MongoDB 8; the timing relative to the shared-database period is open (see S4). (interview: Database)
  • Final step: remove the old deployment and turn off the Jenkins job. (interview: Migration; analysis: §6 CI/CD)

4. Non-functional requirements

Security

  • CI scans dependencies and the container image for known vulnerabilities. (input NFR: Security; interview: Security)
  • Server sends standard security headers on all responses. (input NFR: Security; interview: Security)
  • Export download URLs use the request scheme (HTTPS), not hardcoded http://. (input NFR: Security; interview: Security; analysis: §8 Risks)

Data privacy and compliance

  • Audit log records leave approve/reject/delete and user edit/approve/remove: who, when, which record. (input NFR: Data privacy; interview: Privacy)
  • Admin can export all personal data of one user. (input NFR: Data privacy; interview: Privacy)
  • Admin can erase one user's personal data. (input NFR: Data privacy; interview: Privacy)
  • Regular users see only their own data (see Scope). (input NFR: Data privacy; interview: Data visibility)

Maintainability

  • CI runs on every PR: lint, typecheck, tests, coverage gate, image build and push to registry.instea.co; replaces Jenkins. (input NFR: Maintainability; interview: Maintainability)
  • Shared types package for enums and data used by server and SPA (travel types, leave types/states, login results, countries, diet tariffs); no "keep in sync" copies. (input NFR: Maintainability; interview: Maintainability)
  • Developer docs: README with local setup, architecture decision records. (input NFR: Maintainability; interview: Maintainability)

Localization

  • SPA uses an i18n framework with Slovak and English translations and a language switch. (input NFR: Localization; interview: Localization)
